# Ментальная модель asyncio

Родительская тема: [asyncio](asyncio.md).

## Результаты обучения

После этой части ты сможешь:

- объяснить, какую проблему решает `asyncio` и почему это конкурентность, а не обязательно параллелизм;
- различать coroutine function, coroutine object, `Task` и `Future`;
- по коду определить, где управление может вернуться в event loop;
- объяснить, почему блокирующий вызов останавливает все задачи в потоке loop;
- предсказать порядок и примерное время выполнения небольшого async-кода.

## Зачем backend-разработчику event loop

Backend-сервис много времени не вычисляет, а ждёт: сокет, базу данных, брокер, внешний HTTP API. Если выделять поток на каждый запрос, ожидание занимает поток и его стек. `asyncio` предлагает другую модель: один поток обслуживает много операций, пока большая часть из них ожидает готовности I/O.

Выигрыш появляется не потому, что `async` делает I/O быстрее. Он позволяет во время ожидания одной операции продвигать другие. Это особенно полезно при большом числе одновременно открытых соединений. Для CPU-bound работы это преимущество исчезает: вычисление не отдаёт поток loop и задерживает всех соседей.

## Центральная модель: один диспетчер и много приостанавливаемых задач

Упрощённо event loop повторяет цикл:

1. берёт готовый callback или задачу;
2. выполняет Python-код этой задачи;
3. задача доходит до операции, которая действительно должна ждать, и приостанавливается;
4. loop регистрирует интерес к событию I/O или таймеру и запускает другую готовую работу;
5. когда событие готово, задача снова попадает в очередь готовых.

В одном потоке одновременно исполняется только одна задача. Переключение **кооперативное**: задача сама доходит до точки приостановки. Операционная система не отнимает у неё Python-код в произвольной строке ради другой asyncio-задачи.

> [!important] `await` — возможная, но не гарантированная уступка управления
> `await` передаёт управление только если ожидаемый объект ещё не завершён. Если результат уже готов, выполнение может продолжиться синхронно. Поэтому `await` нельзя считать безусловным «переключателем контекста».

Это объясняет главную аварию async-сервисов: обычный блокирующий вызов не сообщает loop, что он ждёт. Поток застревает внутри `time.sleep()`, синхронного HTTP-клиента или тяжёлого цикла, а остальные задачи не получают ход.

## От `async def` до результата

### Coroutine function и coroutine object

`async def` объявляет **корутинную функцию**. Её вызов не запускает тело, а создаёт **объект корутины** — описание ещё не выполненного вычисления.

```python
import asyncio


async def answer() -> int:
    print("started")
    await asyncio.sleep(0)
    return 42


async def main() -> None:
    coroutine = answer()
    print(type(coroutine).__name__)  # coroutine; "started" ещё не напечатано
    result = await coroutine
    print(result)


asyncio.run(main())
```

`await coroutine` начинает её выполнение и приостанавливает текущую корутину до результата. Если просто вызвать `answer()` и потерять объект, Python позднее выдаст `RuntimeWarning: coroutine ... was never awaited`.

### Task: запланированная корутина

`asyncio.create_task(coro)` оборачивает корутину в `Task` и планирует её выполнение в текущем loop. Вызвавшая корутина продолжает работать до ближайшей фактической уступки управления.

```python
import asyncio


async def worker() -> None:
    print("worker: start")
    await asyncio.sleep(0)
    print("worker: finish")


async def main() -> None:
    task = asyncio.create_task(worker())
    print("main: task created")
    await task
    print("main: task awaited")


asyncio.run(main())
```

Типичный порядок: создание задачи, старт worker, завершение worker, продолжение main. Но бизнес-логика не должна зависеть от случайного порядка независимых готовых задач.

### Future: обещание одного будущего результата

`Future` хранит состояние ожидаемой операции: результат, исключение или отмену. Низкоуровневый callback завершает Future, а ожидающая его Task становится готовой. В прикладном коде Future обычно создаёт loop или библиотека; вручную чаще работают с корутинами и задачами.

Связь объектов можно запомнить так:

```text
coroutine function --call--> coroutine object --schedule--> Task
                                                    |
Task --awaits--> Future/I/O readiness --completion--+
```

## Последовательно или конкурентно

Два `await` подряд означают последовательную зависимость:

```python
first = await fetch("/users")
second = await fetch("/orders")
```

Вторая операция начнётся после первой. Это правильно, если ей нужен `first`. Если операции независимы, их можно запустить в одной области конкурентности:

```python
async with asyncio.TaskGroup() as group:
    users_task = group.create_task(fetch("/users"))
    orders_task = group.create_task(fetch("/orders"))

users = users_task.result()
orders = orders_task.result()
```

Время конкурентного варианта близко к максимуму длительностей операций, а не к их сумме — при условии, что операции действительно неблокирующие и внешняя система допускает параллельные запросы.

## Антипример: `async def` с блокирующим телом

```python
import asyncio
import time


async def bad_worker(name: str) -> None:
    time.sleep(1)  # поток loop заблокирован
    print(name)


async def main() -> None:
    started = time.perf_counter()
    await asyncio.gather(bad_worker("A"), bad_worker("B"))
    print(f"{time.perf_counter() - started:.1f}s")  # около 2.0s


asyncio.run(main())
```

Само ключевое слово `async` ничего не делает неблокирующим. Исправление зависит от природы операции: использовать нативную async-библиотеку, вынести совместимый блокирующий I/O в поток или CPU-bound работу — в отдельный процесс. Это подробно разбирается в [asyncio-backend-patterns-practice](asyncio-backend-patterns-practice.md).

## Самопроверка

1. Почему вызов `async def` не исполняет тело функции?
2. В чём наблюдаемая разница между объектом корутины и `Task`?
3. Может ли строка после `await` выполниться без переключения на другую задачу?
4. Почему `time.sleep(1)` внутри одной задачи задержит сетевые операции других задач в том же loop?
5. Два запроса занимают 300 и 500 мс. Когда их последовательное выполнение предпочтительнее конкурентного?

<details>
<summary>Ориентиры ответов</summary>

1. Вызов создаёт awaitable-объект; исполнение начинается через `await`, Task или runner.
2. Корутина сама не запланирована; Task зарегистрирована в loop и хранит состояние выполнения.
3. Да, если awaitable уже готов; `await` — потенциальная точка приостановки.
4. Блокирующая функция удерживает единственный поток loop и не даёт диспетчеру выполнять другую работу.
5. Когда второй запрос зависит от первого, конкурентность нарушает лимит внешней системы или её накладные расходы не оправданы.

</details>

## Краткое резюме

`asyncio` мультиплексирует множество ожидающих I/O-операций в event loop. Корутина описывает приостанавливаемое вычисление, Task даёт ему независимый жизненный цикл, а Future связывает ожидание с будущим результатом. Пока задача выполняет обычный Python-код, другие задачи в том же потоке стоят. Поэтому корректность и производительность зависят от коротких участков между точками ожидания и от отсутствия блокирующих вызовов.
