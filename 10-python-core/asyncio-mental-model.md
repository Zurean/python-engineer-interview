# Ментальная модель asyncio

Родительская тема: [asyncio](asyncio.md).

## Результаты обучения

После этой части ты сможешь:

- объяснить, какую проблему решает `asyncio` и почему это конкурентность, а не обязательно параллелизм;
- описать роль event loop, его очереди готовой работы, таймеров и I/O-событий;
- различать coroutine function, coroutine object, `Task` и `Future`;
- объяснить разницу между прямым `await child()` и `create_task(child())`;
- по коду определить, где управление может вернуться в event loop;
- объяснить, почему блокирующий вызов останавливает все задачи в потоке loop;
- предсказать порядок и примерное время выполнения небольшого async-кода.

## Что такое event loop и зачем он backend-разработчику

**Event loop** — центральный диспетчер времени выполнения `asyncio`. Он:

- хранит очередь готовых к запуску callbacks и шагов `Task`;
- следит за таймерами;
- через механизм операционной системы узнаёт о готовности сетевого I/O;
- запускает готовую работу и возобновляет задачи, чьи ожидания завершились.

Event loop не является ни потоком, ни корутиной. Это объект-диспетчер, который обычно работает внутри одного OS-потока и по очереди исполняет в нём короткие участки Python-кода. В приложении могут существовать другие потоки и даже другие loops, но конкретный loop привязан к своему потоку, а его задачи не исполняются в нём одновременно.

`asyncio.run(main())` в обычном приложении создаёт loop, планирует в нём корутину `main()`, ведёт loop до её завершения, финализирует async-ресурсы и закрывает loop. Поэтому прикладному коду обычно не нужно вручную вызывать низкоуровневые методы loop.

Backend-сервис много времени не вычисляет, а ждёт: сокет, базу данных, брокер, внешний HTTP API. При модели «поток на запрос» ожидание занимает поток и его стек. Event loop позволяет одному потоку обслуживать множество операций, пока большая часть из них ожидает готовности I/O.

Выигрыш появляется не потому, что `async` делает I/O быстрее. Он позволяет во время ожидания одной операции продвигать другие. Для CPU-bound работы это преимущество исчезает: длительное вычисление не отдаёт поток loop и задерживает все остальные задачи в нём.

## Одна итерация event loop

Конкретные внутренности зависят от реализации loop, но концептуально каждая итерация сводится к следующему:

1. loop определяет, есть ли готовая работа и как долго можно ждать ближайший таймер;
2. получает от ОС события готовности зарегистрированного I/O;
3. переносит I/O-callbacks и истёкшие таймеры в очередь готовых;
4. по очереди запускает очередную порцию готовых callbacks и шагов `Task`;
5. если задача снова ждёт незавершённый объект, оставляет её приостановленной; если завершилась — сохраняет результат или исключение.

Loop не исполняет корутину целиком за один «оборот». `Task` продвигает её только до завершения или до ожидания незавершённого awaitable. Когда низкоуровневое I/O завершится, callback отметит связанный `Future` готовым, а тот запланирует следующий шаг ожидающей `Task`.

Переключение **кооперативное**: задача сама должна дойти до реальной точки приостановки. Операционная система не отнимает у неё Python-код в произвольной строке ради другой asyncio-задачи.

> [!important] `await` — возможная, но не гарантированная уступка управления
> `await` передаёт управление loop только если ожидаемый объект ещё не завершён. Если результат уже готов или корутина может получить его без ожидания, выполнение продолжится синхронно. Поэтому `await` нельзя считать безусловным «переключателем контекста».

Обычный блокирующий вызов не регистрирует ожидание в loop и не возвращает ему управление. Поток застревает внутри `time.sleep()`, синхронного HTTP-клиента или тяжёлого цикла, а остальные задачи не получают ход.

## От `async def` до результата

### Coroutine function и coroutine object

`async def` объявляет **корутинную функцию**. Её вызов не запускает тело, а создаёт **объект корутины** — описание ещё не выполненного вычисления.

```python
import asyncio


async def answer() -> int:
    # Тело начинает выполняться только после await или планирования в Task.
    print("started")

    # sleep(0) приостанавливает текущую Task и отдаёт управление loop.
    await asyncio.sleep(0)

    # После повторного планирования выполнение продолжается с этой строки.
    print("resumed")
    return 42


async def main() -> None:
    # Вызов async-функции создаёт объект корутины, но не исполняет её тело.
    coroutine = answer()
    print(f"created: {type(coroutine).__name__}")

    # Прямой await исполняет answer() внутри текущей Task main.
    result = await coroutine
    print(f"result: {result}")


# run() создаёт loop и ведёт его до завершения main().
asyncio.run(main())
```

Результат:

```text
created: coroutine
started
resumed
result: 42
```

`await coroutine` начинает её выполнение и возвращает результат в текущую корутину. Если просто вызвать `answer()` и потерять объект, Python позднее выдаст `RuntimeWarning: coroutine ... was never awaited`.

### Обычный `await`: вложенный вызов в той же Task

В выражении `result = await child()` слово `await` не превращает `child()` в отдельную `Task`. Дочерняя корутина начинает исполняться в контексте текущей задачи, как вложенный вызов функции с возможностью приостановки. Пока `child()` не завершится, родительская корутина не перейдёт к следующей строке.

Если `child()` дойдёт до незавершённого `Future`, приостановится вся цепочка вложенных корутин текущей `Task`. Loop сможет выполнять другие задачи, но отдельного жизненного цикла, имени, отмены или конкурентного выполнения у `child()` нет.

### Task: отдельный запланированный жизненный цикл

`asyncio.create_task(coro)` оборачивает корутину в `Task`, регистрирует её в текущем loop и возвращает объект управления. Новая задача получает собственное состояние: её можно независимо ожидать, отменить, проверить на завершение и получить из неё результат или исключение. Вызвавшая корутина продолжает работать до ближайшей фактической уступки управления.

```python
import asyncio


async def worker() -> int:
    # Этот код выполнится, когда loop впервые даст ход новой Task.
    print("worker: start")

    # Task приостанавливается и снова становится готовой на следующем обороте loop.
    await asyncio.sleep(0)

    print("worker: finish")
    return 42


async def main() -> None:
    # Создаём отдельную Task; worker() запланирован, но ещё не обязан стартовать.
    task = asyncio.create_task(worker(), name="worker")
    print("main: task created")

    # Ожидаем уже запущенную Task и получаем сохранённый в ней результат.
    result = await task
    print(f"main: result = {result}")


# Запускаем верхнеуровневую корутину main().
asyncio.run(main())
```

Результат с обычной фабрикой задач:

```text
main: task created
worker: start
worker: finish
main: result = 42
```

Здесь `main` печатает сообщение после `create_task()`, а затем уступает управление на `await task`. Бизнес-логика не должна зависеть от случайного порядка независимых готовых задач. Python также поддерживает eager task factory, при которой корутина может начать исполняться уже во время создания `Task`; это специальная настройка, а не модель по умолчанию.

### Future: обещание одного будущего результата

`Future` — низкоуровневый awaitable-контейнер для **одного результата, исключения или отмены**, которые появятся позднее. Сам `Future` не исполняет корутину и ничего активно не делает. Производитель результата — transport, callback, библиотека или другая задача — вызывает `set_result()` либо `set_exception()`. После этого loop ставит ожидающую `Task` обратно в очередь готовых.

`Task` является специализированным подклассом `Future`: она тоже предоставляет `done()`, `result()`, `exception()`, callbacks и ожидание через `await`, но дополнительно **активно продвигает корутину**. Вручную вызывать у Task `set_result()` и `set_exception()` нельзя: итог определяет исполненная корутина. Коротко: `Future` представляет будущий результат, а `Task` представляет запланированное выполнение корутины и наследует контейнер для её итогового результата.

В прикладном коде `Future` вручную создают редко: обычно его прячет async-драйвер или библиотека. Следующий учебный пример специально показывает низкоуровневую механику:

```python
import asyncio


async def main() -> None:
    # Получаем loop, который сейчас исполняет main().
    loop = asyncio.get_running_loop()

    # Создаём пассивный контейнер результата, привязанный к этому loop.
    future: asyncio.Future[str] = loop.create_future()

    # Через 0.1 с callback положит значение в Future.
    # В реальной библиотеке такой callback обычно вызывается при готовности I/O.
    loop.call_later(0.1, future.set_result, "data is ready")
    print(f"before await: done={future.done()}")

    # Future ещё не готов: Task main приостанавливается, а loop ждёт таймер.
    result = await future

    # После set_result() main снова попала в очередь готовых и продолжилась.
    print(f"after await: done={future.done()}, result={result}")


# Создаём loop и запускаем main().
asyncio.run(main())
```

Результат:

```text
before await: done=False
after await: done=True, result=data is ready
```

## Схема связи объектов и прохождения результата

У обычного `await` и отдельной `Task` разные пути исполнения:

```text
Путь 1 — прямой await, отдельной Task не появляется:

Task main
└── исполняет main()
    └── await child() → исполняет child() в той же Task
        └── await Future → вся Task main приостановлена

Путь 2 — create_task(), появляются две независимо планируемые Task:

Task main ── await ──► Task child ── исполняет ──► child()
                           └── await Future → приостановлена только Task child

Завершение ожидания:

I/O или таймер
    └── callback вызывает Future.set_result(value)
        └── loop делает ожидающую Task готовой
            └── Task возобновляет корутину и передаёт value из await
```

Как читать схему:

1. Вызов `child()` создаёт coroutine object — описание приостанавливаемого вычисления.
2. `await child()` входит в эту корутину в рамках текущей `Task`; конкурентный «ребёнок» не создаётся.
3. `create_task(child())` создаёт вторую сущность, которую loop может продвигать независимо от родителя.
4. Незавершённый `Future` временно отвязывает ожидающую задачу от процессора: задача ждёт, а loop занимается другой готовой работой.
5. Результат движется обратно по цепочке `Future → Task → выражение await`. Если вместо значения сохранено исключение, `await` поднимает это исключение; при отмене — `CancelledError`.

| Объект | Что представляет | Сам запланирован в loop | Что даёт `await` |
|---|---|---:|---|
| coroutine object | ещё не завершённое вычисление из `async def` | нет | исполняет его в текущей Task до результата |
| `Future[T]` | значение `T`, исключение или отмену в будущем | нет | ждёт, пока кто-то завершит Future |
| `Task[T]` | запланированное исполнение корутины | да | ждёт завершения Task и возвращает её результат |

## Последовательно или конкурентно

Два прямых `await` подряд означают последовательное выполнение:

```python
import asyncio
import time


async def fetch(name: str, delay: float) -> str:
    # Имитируем неблокирующий сетевой запрос.
    print(f"{name}: start")
    await asyncio.sleep(delay)
    print(f"{name}: finish")
    return f"{name} data"


async def main() -> None:
    started = time.perf_counter()

    # Второй вызов начнётся только после полного завершения первого.
    users = await fetch("users", 0.1)
    orders = await fetch("orders", 0.2)

    elapsed = time.perf_counter() - started
    print(f"result: {users}, {orders}; elapsed ~ {elapsed:.1f}s")


# Запускаем последовательный сценарий.
asyncio.run(main())
```

Результат:

```text
users: start
users: finish
orders: start
orders: finish
result: users data, orders data; elapsed ~ 0.3s
```

Это правильно, если второй операции нужен результат первой. Если операции независимы, их можно запустить в одной области конкурентности:

```python
import asyncio
import time


async def fetch(name: str, delay: float) -> str:
    # Имитируем неблокирующий сетевой запрос.
    print(f"{name}: start")
    await asyncio.sleep(delay)
    print(f"{name}: finish")
    return f"{name} data"


async def main() -> None:
    started = time.perf_counter()

    # TaskGroup создаёт две отдельные Task и ждёт обе при выходе из блока.
    async with asyncio.TaskGroup() as group:
        users_task = group.create_task(fetch("users", 0.1))
        orders_task = group.create_task(fetch("orders", 0.2))

    # После блока обе задачи завершены, поэтому result() безопасен.
    users = users_task.result()
    orders = orders_task.result()

    elapsed = time.perf_counter() - started
    print(f"result: {users}, {orders}; elapsed ~ {elapsed:.1f}s")


# Запускаем конкурентный сценарий (TaskGroup доступен с Python 3.11).
asyncio.run(main())
```

Результат:

```text
users: start
orders: start
users: finish
orders: finish
result: users data, orders data; elapsed ~ 0.2s
```

Время конкурентного варианта близко к максимуму длительностей операций, а не к их сумме — при условии, что операции действительно неблокирующие и внешняя система допускает параллельные запросы.

## Антипример: `async def` с блокирующим телом

```python
import asyncio
import time


async def bad_worker(name: str) -> None:
    # Это синхронный сон: он удерживает поток и не возвращает управление loop.
    time.sleep(1)
    print(f"{name}: done")


async def main() -> None:
    # Замеряем суммарное время двух формально конкурентных корутин.
    started = time.perf_counter()

    # gather планирует обе корутины, но первая блокирует единственный поток loop.
    await asyncio.gather(bad_worker("A"), bad_worker("B"))

    # Поэтому workers фактически отрабатывают последовательно.
    print(f"elapsed ~ {time.perf_counter() - started:.1f}s")


# Создаём loop и запускаем main().
asyncio.run(main())
```

Результат:

```text
A: done
B: done
elapsed ~ 2.0s
```

Само ключевое слово `async` ничего не делает неблокирующим. Исправление зависит от природы операции: использовать нативную async-библиотеку, вынести совместимый блокирующий I/O в поток или CPU-bound работу — в отдельный процесс. Это подробно разбирается в [asyncio-backend-patterns-practice](asyncio-backend-patterns-practice.md).

## Самопроверка

1. Почему вызов `async def` не исполняет тело функции?
2. Чем прямой `await child()` отличается от `create_task(child())`?
3. Может ли строка после `await` выполниться без переключения на другую задачу?
4. Почему `time.sleep(1)` внутри одной задачи задержит сетевые операции других задач в том же loop?
5. Чем пассивный `Future` отличается от `Task`?
6. Два запроса занимают 300 и 500 мс. Когда их последовательное выполнение предпочтительнее конкурентного?

<details>
<summary>Ориентиры ответов</summary>

1. Вызов создаёт awaitable-объект; исполнение начинается через `await`, Task или runner.
2. Прямой `await` исполняет дочернюю корутину внутри текущей Task и не даёт родителю перейти дальше; `create_task()` создаёт отдельный независимо планируемый жизненный цикл.
3. Да, если awaitable уже готов; `await` — потенциальная точка приостановки.
4. Блокирующая функция удерживает единственный поток loop и не даёт диспетчеру выполнять другую работу.
5. Future только хранит будущий исход и завершается внешним производителем; Task продвигает корутину и является Future для её итогового исхода.
6. Когда второй запрос зависит от первого, конкурентность нарушает лимит внешней системы или её накладные расходы не оправданы.

</details>

## Краткое резюме

Event loop — диспетчер готовых шагов задач, callbacks, таймеров и I/O-событий. Корутина описывает приостанавливаемое вычисление; прямой `await` исполняет её в текущей Task; `create_task()` даёт ей отдельный планируемый жизненный цикл; Future связывает ожидание с результатом, который появится снаружи. Пока задача выполняет обычный Python-код, другие задачи в том же потоке стоят. Поэтому корректность и отзывчивость зависят от коротких участков между реальными точками приостановки и от отсутствия блокирующих вызовов.
