# RAG: retrieval-augmented generation

> **Зачем на собесе:** основной паттерн LLM-приложений; обязателен в Магните и 1440. Вопросы практические: чанкинг, эмбеддинги, поиск, качество, галлюцинации, стоимость.

## Минимум для собеса

- **Зачем RAG:** дать модели актуальные/приватные данные без дообучения; снизить галлюцинации через цитирование источников; контролировать доступ к данным на уровне retrieval.
- **Пайплайн индексации:** загрузка → парсинг (PDF/DOCX/HTML; таблицы и сканы — боль, OCR) → чанкинг (по структуре документа, 200–800 токенов, overlap; заголовки в чанк; метаданные: источник, страница, дата, tenant) → эмбеддинги (модель, размерность, язык — для русского проверять) → хранилище (pgvector для начала; Qdrant/Weaviate/Milvus при масштабе — [vector-dbs](../95-optional/vector-dbs.md)). Асинхронно, через очередь, идемпотентно по hash документа ([kafka](../50-messaging-caching/kafka.md)).
- **Пайплайн запроса:** (переформулировка запроса) → retrieval: векторный поиск (cosine, HNSW-индекс) + **гибрид** с BM25/полнотекстом → фильтры по метаданным и правам → **rerank** (cross-encoder) → сборка контекста с лимитом токенов → промпт с инструкцией «отвечай по источникам, иначе скажи, что не знаешь» → ответ с цитатами → логирование.
- **Качество:** retrieval-метрики (recall@k, MRR), ответ (faithfulness/groundedness, relevance) — через evals на размеченном наборе вопросов ([evals-cost-latency](evals-cost-latency.md)). Главная причина плохих ответов — плохой retrieval, а не модель.
- **Типовые проблемы и решения:** неверный чанкинг (контекст рвётся) → структурный чанкинг; вопрос не похож на текст → HyDE/переформулировка/гибрид; много похожих документов → rerank, дедупликация; устаревшие данные → инкрементальная переиндексация; галлюцинации → жёсткие инструкции, цитаты, проверка groundedness, «не знаю» как допустимый ответ.
- **Стоимость и латентность:** кэш эмбеддингов запросов и ответов (Redis), ограничение k, маленькая модель для rerank/классификации, большая — для ответа; стриминг ответа; батчинг индексации.
- **Безопасность:** фильтрация по правам до генерации (не после), prompt injection через документы, PII в логах.
- **Инструменты:** можно без фреймворков (httpx + SDK + pgvector); LangChain/LlamaIndex — знать, уметь объяснить, почему да/нет. Свой код прозрачнее для отладки.
- **Когда RAG не нужен:** мало данных — положить в контекст целиком (long context); структурированные данные — text-to-SQL/tool calling; стабильные знания — fine-tuning (редко).

## Вопросы с собесов

- [ ] Опиши RAG-пайплайн от загрузки документа до ответа. → *индексация + запрос, по шагам*
- [ ] Как чанкуешь документы и почему? → *по структуре, размер, overlap, метаданные*
- [ ] Ответы плохие. Как найти, где проблема? → *сначала retrieval (recall@k), потом промпт/модель; evals*
- [ ] Что такое гибридный поиск и зачем rerank? → *вектор + лексика; точность top-k*
- [ ] Как боретесь с галлюцинациями? → *grounding, цитаты, инструкции, «не знаю», проверка*
- [ ] pgvector или отдельная векторная БД? → *pgvector до миллионов векторов и пока всё в Postgres; отдельная — масштаб/фильтры/производительность*
- [ ] Как обеспечить, что пользователь не увидит чужие документы? → *фильтр по правам в retrieval, tenant в метаданных*
- [ ] Как обновляешь индекс при изменении документов? → *события, hash, инкрементально, версионирование*
- [ ] Расскажи про свой опыт с LLM: что получилось, что нет. → *[stories](../00-strategy/stories.md), история 2*
- [ ] RAG vs fine-tuning vs long context? → *данные/знания/стиль; стоимость*

## Углубление

- Эмбеддинги: как выбирать модель (MTEB, язык, размерность), квантование, matryoshka; HNSW vs IVF, параметры `ef_search`/`m`.
- Продвинутые схемы: parent-child chunks, contextual retrieval, GraphRAG, agentic RAG (модель решает, что искать), multi-query.
- Оценка: RAGAS, собственные LLM-as-judge, A/B на реальных запросах.
- Multimodal RAG (таблицы, изображения), text-to-SQL как альтернатива для структурированных данных.
