# Evals, контроль стоимости и латентности LLM-систем

> **Зачем на собесе:** Магнит и 1440 требуют evals явно; на любом AI-собесе вопрос «как вы понимали, что стало лучше/хуже?» отделяет инженера от энтузиаста. Это аналог тестов и observability для LLM-слоя.

## Минимум для собеса

- **Зачем evals:** LLM недетерминированы, промпт/модель/данные меняются; без измерений любое изменение — гадание. Evals = тесты для поведения модели.
- **Набор данных:** 50–200 реальных (или реалистичных) запросов с ожидаемыми ответами/критериями; собирать из прода (с разметкой), покрывать сложные и граничные случаи; версионировать; пополнять из инцидентов («регрессионные кейсы»).
- **Метрики по типу задачи:** классификация/извлечение — accuracy/F1 по полям (structured output упрощает); RAG — recall@k для retrieval, faithfulness/relevance для ответа; генерация — rubric-based оценка; агенты — успех задачи, число шагов, стоимость.
- **Оценщики:** код (точное сравнение, схема, регулярки), **LLM-as-judge** (рубрика, pairwise сравнение; калибровать по человеческой разметке; судья ≠ оцениваемая модель по возможности), человек (выборочно, для калибровки).
- **Процесс:** evals в CI на изменение промпта/модели/retrieval → отчёт по метрикам и стоимости → только потом выкатка; онлайн — A/B, feedback (👍/👎), мониторинг доли «не знаю»/ошибок/жалоб.
- **Стоимость:** токены вход/выход × цена; измерять на запрос и на пользователя; снижать — кэш ответов и эмбеддингов, prompt caching, маленькие модели для простых шагов (роутинг/классификация), ограничение контекста, batch API для офлайн-обработки, лимиты на пользователя.
- **Латентность:** p50/p95 на вызов и end-to-end; стриминг первого токена (TTFT); параллельные вызовы там, где независимы; меньше итераций агента; быстрые модели; таймауты и фолбэки ([resilience-patterns](../30-backend-design/resilience-patterns.md)).
- **Observability для LLM:** трейс каждого запроса (промпт, ответ, токены, стоимость, латентность, версия промпта/модели), Langfuse/Phoenix/OTel; алерты на рост стоимости и ошибок; маскирование PII ([observability](../40-infra/observability.md)).
- **Типовые провалы:** evals на 5 примерах; метрика не связана с бизнес-целью; судья хвалит всё; изменили промпт «на глаз» — сломали другой кейс; стоимость узнали из счёта.

## Вопросы с собесов

- [ ] Как оценивали качество LLM-фичи? Как понимали, что изменение промпта не сломало другое? → *датасет, метрики, CI, регрессии*
- [ ] Что такое LLM-as-judge, какие у него проблемы? → *рубрика; смещения, калибровка по людям*
- [ ] Какие метрики для RAG? → *recall@k, faithfulness, relevance*
- [ ] Как контролируешь стоимость? → *измерять, кэш, маленькие модели, лимиты, batch*
- [ ] Как снижаешь латентность? → *стриминг, параллелизм, меньше шагов, быстрые модели*
- [ ] Что логируешь для LLM-вызовов и как это используешь? → *трейс, токены, стоимость, версии → отладка и evals*
- [ ] Как собираешь датасет для evals? → *прод + разметка, инциденты, edge cases*
- [ ] Как бы ты рассказал о своём AI-кейсе в терминах evals? → *[stories](../00-strategy/stories.md), история 2: выборка, проверка, доля ошибок*

## Углубление

- Статистика evals: размер выборки, доверительные интервалы, pairwise с bootstrap.
- Онлайн-метрики и их связь с офлайн; guardrail-метрики.
- Оценка агентов: трассы, промежуточные шаги, инструментальные ошибки.
- Red teaming и safety evals.
- Fine-tuning малых моделей на своих данных как способ снизить стоимость — когда оправдано.
